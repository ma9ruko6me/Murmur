# 第1章 認証・認可とセキュリティ（8問）

## Q1. セッション認証とトークン認証

「セッション認証」と「トークン（JWT）認証」の違いを説明してください。また、このアプリでJWTを採用した理由（利点）も述べてください。

**回答:**

セッション認証はログイン成功時にサーバーがセッションIDを発行し、サーバー内にログイン情報を保持してリクエストのたびにその情報を照らし合わせて本人確認を行います。これに対して、トークン認証ではログイン成功時にサーバーがユーザー情報と署名を含んだトークンを発行します。これには有効期限が設定されており、リクエストのたびに署名を検証して本人確認を行います。サーバー側で状態を管理しない点がセッション認証との違いで、複数ユーザーが使用し、APIサーバーも複数台使用する想定でこのアプリを実装しているので、サーバー側がセッション状態を持たず、どのサーバーでも検証が行えるトークン認証が適しています。

## Q2. アクセストークンとリフレッシュトークン

以下について説明してください：

- なぜトークンを2種類に分けるのか
- アクセストークンの有効期限が短い理由

（アクセストークン: 15分 / リフレッシュトークン: 7日）

**回答:**

トークンの有効期限は長いと盗まれた時の被害を受ける期間が長くなり、安全性が低下します。反対に有効期限が短いとユーザーに頻繁にログインすることを要求し、利便性が低下します。そのため、有効期限が長いものと短いものの2種類に分けて発行することで安全性と利便性の両立を実現しています。有効期限の短いアクセストークンはDBを参照せずに検証するため、サーバー側が一方的に無効化することができません。そのため、仮に盗まれても被害を最小限にするために有効期限を短く設定します。

## Q3. パスワードのハッシュ化

「ハッシュ化」と「暗号化」の違いを説明してください。また、なぜパスワード保存にハッシュ化を使うのか述べてください。

**回答:**

ハッシュ化とは一方的な変化を加えて元の形に戻すことができない形に変更する手法です。この変化には再現性はありますが、変化を加えたものを元の形に戻すことはできません。暗号化は特定の方法で変化を加えて別の形にする方法で、これは対応した別の方法で元の形に戻すことができます。パスワードを保存するとき、暗号化ではDBが漏洩した場合、特定の方法で元のパスワードが復元できますが、ハッシュ化ではDBに保存されているものから元のパスワードを復元することができません。そのため、パスワード保存ではハッシュ化が用いられます。

---

## Q4. 認可（Authorization）

「認証」と「認可」の違いを説明し、「自分の投稿のみ編集・削除できる」機能がどちらに該当するか答えてください。

**回答:**

認証はユーザーが本人であるかの確認であるのに対して、認可は機能の使用を許可する仕組みです。自分の投稿のみ編集・削除できる機能はその投稿を編集・削除する権限があるかを確認する仕組みを持つため認可に該当します。

## Q5. CORS設定の実務理解

以下について説明してください：

- 本番環境でのCORS設定の変更点
- `allowedOrigins("*")`の問題点

**回答:**

フロントエンドとバックエンドは別のオリジンで起動しているシステムであるため、本来はフロントエンドがバックエンドに接続できないが、CORS設定により特定のオリジンへの接続を許可します。本番環境では実際に使用するオリジンのみ許可する設定にし、第三者のサイトから意図しないAPI呼び出しをされないように変更します。現在の`allowedOrigins("*")`が第三者からの接続も許可している状態で、どこからでも接続できる状態になっていることが問題です。

## Q6. SQLインジェクション

SQLインジェクションとは何か説明してください。また、MyBatisで防ぐための実装上の注意点を述べてください。

**回答:**

SQLインジェクションとはユーザーの入力値をそのままSQL文に埋め込んでしまうことで、意図しないSQLが実行されてしまう脆弱性のことです。MyBatisではSQL構文の一部として認識される`${}`(文字列展開)ではなく、入力値を値としてバインドすることができる`#{}`(プレースホルダ)を使うことでユーザーの自由入力を直接使わないようにする必要があります。

# 第2章 アプリケーションアーキテクチャ（7問）

## Q9. レイヤードアーキテクチャ

Controller / Service / Repository の役割を説明してください。また、以下も答えてください：

- なぜ分離するのか
- ControllerとServiceの責務の境界

**回答:**

Controllerはユーザーからのリクエストを受け取る窓口のようなもので入力チェックを行い、Serviceにリクエストを送ります。Serviceでは業務ロジックで受け取ったリクエストをレスポンスを適切な形にデータを詰め替えたり、初期値の設定などを行います。Repositoryでは直接DBとやり取りをし、データの登録や取得などを行います。3層に分離することで機能変更やバグの修正などを行いやすくなります。Controllerは入出力の形式に関わる部分を、Serviceはビジネスルールに関わる部分を担います。例えば、自分の投稿かどうかを確認するシステムにおいて、IDが正しい型であることの確認はControllerで行い、自分のIDとの比較はServiceで行います。

---

## Q10. DTOパターン

エンティティを直接APIに使わない理由を説明してください。

**回答:**

エンティティとはDBの持つテーブル情報に合わせてプログラム内で扱うデータの型を指定したものです。エンティティを直接APIに使用すると毎回パスワードや関係のない情報も通信する必要があるため、機密情報が流出する危険性や意図しないデータの変更が起きる可能性があります。また、DBのテーブル構造が変更したときにエンティティの変更に合わせてAPIも変更する必要が生まれるため、それぞれのAPIに適した情報のみを持ったDTOを設定することが適切です。

## Q12. MyBatis vs JPA

以下の観点で違いを説明してください：

- SQL制御
- 学習コスト

**回答:**

MyBatisは決められたSQL文でDBを操作するため、操作に必要なSQL文は全てコーディングする必要があります。SQLの知識が必要ではありますが、トラブルが起きたときに原因を負いやすく、トータルの学習コストが小さくなる傾向があります。一方でJPAはDBを操作するタイミングでその操作に適したSQL文を自動で作成するため、Javaのコードのみで動くシステムを作ることができます。しかし、トラブルが発生したときに原因を追うことが難しく、ORMの内部動作など別の知識が必要になり、結果的に学習コストが大きくなる傾向があります。

## Q14. Flyway（DBマイグレーション）

マイグレーションツールを使う理由を説明してください。（直接ALTER TABLEしない理由）

**回答:**

マイグレーションツールを利用すると容易にDB構成を変更することができます。また、変更履歴も残すことができるので変更によるトラブルの原因の特定がしやすく、過去のDB構成を再度使用することも可能になります。さらに、複数環境でのDB構成のずれを生じさせず、同じ順序で同じSQLを適用することができるようになります。
